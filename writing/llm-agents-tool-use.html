LLM Agents & Tool Use

Agent architectures, function calling, orchestration frameworks, memory systems, and guardrails — how LLMs go from generating text to taking action.

Anvesh Jarabani · July 2026 · 13 min read
Overview

An LLM agent is a system that combines a language model with tools and a control loop. The model observes its environment, reasons about what to do, acts by calling a tool, and then repeats until the task is complete. This transforms LLMs from stateless text generators into autonomous problem solvers that can interact with databases, APIs, file systems, and the real world.

The core insight is simple: an LLM alone can only produce text. But give it a set of well-defined tools and a feedback loop, and it becomes capable of multi-step reasoning, error recovery, and task completion across arbitrarily complex workflows. The model decides which tool to call, what arguments to pass, and what to do next based on the result.

The Agent Loop

Why agents matter: Traditional LLM applications are single-turn: prompt in, text out. Agents break this constraint. A coding agent can write code, run tests, read errors, and fix bugs — iterating until the tests pass. A research agent can search the web, read papers, cross-reference claims, and produce a cited report. The agent pattern is how LLMs move from answering questions to completing tasks.
LLM (The Brain)
  • Understands natural language instructions
  • Reasons about which tool to use
  • Generates structured tool call arguments
  • Interprets results and decides next step
Tools (The Hands)
  • APIs, databases, file systems, browsers
  • Code execution sandboxes
  • Search engines and knowledge bases
  • External services (email, Slack, Jira)
Control Loop (The Spine)
  • Orchestrates observe-reason-act cycle
  • Manages conversation state and history
  • Enforces guardrails and permissions
  • Handles errors, retries, and escalation
Agent Architectures

Four dominant architecture patterns have emerged, each trading off simplicity vs. capability. The right choice depends on task complexity, latency requirements, and how much control you need over the execution path.

ReAct
Reason + Act
The model interleaves reasoning traces with tool actions in a single loop. At each step, it thinks out loud ("I need to look up the user's order history"), calls a tool, observes the result, then reasons about the next action. Simple, debuggable, and the most widely deployed pattern.

Best for: Single-agent tasks, API integrations, chatbot tool use. Low overhead, easy to trace.

Plan-and-Execute
Plan First
A planning step generates a complete task decomposition before any execution begins. A separate executor then works through the plan step by step, optionally re-planning if a step fails. This avoids the greedy local decisions of ReAct and handles complex multi-step tasks more reliably.

Best for: Multi-step workflows, research tasks, data pipelines. More tokens upfront, better outcomes on complex tasks.

Multi-Agent
Collaboration
Multiple specialized agents collaborate on a task, each with its own system prompt, tools, and expertise. A supervisor agent routes sub-tasks to the right specialist. Agents communicate through a shared message bus or structured handoffs. Enables division of labor and tool isolation.

Best for: Software development, complex analysis, tasks requiring multiple domains of expertise.

Hierarchical
Delegation Tree
A tree of agents with explicit delegation. Manager agents decompose work and spawn worker agents, which may themselves delegate further. Each level has its own context window, tools, and permission scope. Enables deep specialization while keeping each agent's context focused.

Best for: Enterprise workflows, large codebases, tasks that naturally decompose into independent sub-problems.

Pattern selection heuristic: Start with ReAct. If the task has more than 5 steps, try Plan-and-Execute. If it needs multiple tools with different permission scopes, use Multi-Agent. If sub-tasks are themselves complex multi-step problems, go Hierarchical. Simpler is always better — every layer of indirection adds latency and failure modes.
Tool Use & Function Calling

Function calling is the mechanism that bridges the gap between language generation and real-world action. The model doesn't execute code directly — it generates a structured request that the runtime executes on its behalf. This separation is what makes agents both powerful and controllable.

How a Tool Call Works

1. System — Tool Definition
{
  "name": "query_database",
  "description": "Execute a read-only SQL query",
  "parameters": {
    "type": "object",
    "properties": {
      "sql": { "type": "string", "description": "SQL SELECT query" },
      "database": { "type": "string", "enum": ["analytics", "users"] }
    },
    "required": ["sql", "database"]
  }
}
2. Model — Tool Call
{
  "type": "tool_use",
  "name": "query_database",
  "input": {
    "sql": "SELECT COUNT(*) as active_users FROM users WHERE last_seen > NOW() - INTERVAL '7 days'",
    "database": "users"
  }
}
3. Runtime — Execution
Runtime validates arguments against JSON Schema, checks permissions, executes the query against the database, captures the result.
4. Result — Back to Model
{
  "type": "tool_result",
  "content": "[{\"active_users\": 14832}]"
}
Parallel Tool Calling

Models can request multiple tool calls in a single turn when the calls are independent. The runtime executes them concurrently and returns all results at once.

  • Reduces round trips — 3 API lookups in 1 turn
  • Model decides independence (no shared state)
  • Runtime collects results, returns as array
  • Falls back to sequential if dependencies exist
Error Handling

Tool calls fail. Good agents handle failures gracefully with a retry → fallback → escalate strategy.

  • Retry: Transient errors (timeout, rate limit) — wait and retry
  • Reformulate: Bad arguments — fix based on error message
  • Fallback: Try an alternative tool or approach
  • Escalate: Ask the user for help or clarification
Tool design matters more than model choice. A well-described tool with clear parameter names, tight JSON Schema constraints, and helpful error messages will work reliably across models. A vaguely described tool will fail even with the best model. Write tool descriptions like API documentation for a junior developer — explicit, unambiguous, with examples in the description.
Tool Definition Best Practices
  • Use descriptive names: search_orders not tool_1
  • Include parameter descriptions with examples
  • Use enum to constrain categorical inputs
  • Mark required vs optional clearly
  • Keep tool count under 20 per agent turn
MCP (Model Context Protocol)
  • Standardized protocol for tool registration
  • Server exposes tools, resources, prompts
  • Client connects over stdio or SSE transport
  • Tools auto-discovered at connection time
  • One server can serve multiple agent frameworks
Tool Result Formatting
  • Return structured data (JSON), not prose
  • Include metadata: row count, truncation flag
  • Cap result size to avoid context overflow
  • Return errors as structured objects, not exceptions
  • Paginate large results with cursor tokens
Orchestration Frameworks

Orchestration frameworks handle the plumbing: state management, tool execution, agent coordination, and persistence. They differ significantly in their execution model, state management approach, and target use cases. Choosing the right one depends on whether you need graphs, conversations, or simple tool loops.

Framework Model State Multi-Agent Strengths
LangGraph Graph-based state machines Persistent checkpoints Nested graphs, subgraphs Cycles, branching, human-in-the-loop
CrewAI Role-based crews Shared crew memory Built-in role delegation Declarative task definitions, fast setup
Autogen Multi-agent conversations Chat history Native group chat Conversational agents, code execution

LangGraph

Models agent workflows as directed graphs with cycles. Nodes are functions (LLM calls, tool executions, routing logic). Edges define transitions. State is a typed dictionary that flows through the graph.

  • Supports cycles — agent can loop back to re-plan
  • Checkpointing for pause/resume and time-travel debugging
  • Subgraphs enable hierarchical composition
  • Human-in-the-loop via interrupt_before / interrupt_after
CrewAI

Define agents as roles with goals, then assign them tasks. The framework handles delegation, context sharing, and execution order. Feels like managing a team.

  • Declarative: define agents and tasks in YAML or Python
  • Built-in role-based delegation (manager → worker)
  • Shared memory across crew members
  • Sequential or hierarchical process modes
Autogen

Microsoft's framework for multi-agent conversations. Agents talk to each other in a group chat, with a manager deciding who speaks next.

  • Group chat with speaker selection
  • Code execution via Docker sandboxes
  • Nested chat for hierarchical delegation
  • Teachable agents that learn from feedback
Claude Agent SDK

Anthropic's official SDK for building agents with Claude. The tool_runner pattern handles the observe-act loop, and handoffs enable multi-agent coordination.

  • First-class MCP server integration
  • client.messages.tool_runner() handles the full loop
  • Agent handoffs with context transfer
  • Built-in guardrails and content filtering
Google ADK

Agent Development Kit with tight Vertex AI integration. Agents compose with tools, sub-agents, and Google Cloud services.

  • BigQuery and Vertex AI toolsets built in
  • Session-based state management
  • Agent composition with explicit routing
  • Deploy to Vertex AI Agent Engine
Framework selection: If you need complex branching and human-in-the-loop, use LangGraph. If you want fast multi-agent setup with minimal code, try CrewAI. If you're building on Claude, the Agent SDK gives you the tightest integration. If you're in the Google Cloud ecosystem, ADK connects natively. And if your agents need to debate each other, Autogen's conversational model is purpose-built for that.
Agent Memory Systems

Memory is what separates a useful agent from a forgetful chatbot. Without memory, every interaction starts from zero. With the right memory architecture, agents learn from past actions, maintain context across long tasks, and adapt to user preferences over time. Five memory types serve different temporal and functional needs.

Conversation Memory
Within session
The chat history. Every message, tool call, and result in the current conversation. The most basic form of memory — but context windows are finite.
Sliding window (keep last N turns) or summarization (compress old messages)
Semantic Memory
Cross-session
Past interactions embedded into a vector store. The agent retrieves relevant memories by semantic similarity. Enables "I remember we discussed X last week."
Embed messages → store in pgvector/Pinecone/Chroma → RAG retrieval
Episodic Memory
Cross-session
Structured records of past actions and outcomes. Not free-text — structured data: "Ran deploy at 3pm, failed with OOM, fixed by increasing memory to 4GB."
Structured logs in a database — action, params, result, timestamp
Working Memory
Within task
A scratchpad for the current task. The agent writes notes to itself: intermediate results, partial plans, variables to track. Survives tool calls but not session restarts.
Key-value store or markdown scratchpad injected into system prompt
Persistent Memory
Permanent
Long-lived knowledge that spans all sessions: user preferences, project conventions, learned patterns. The agent's accumulated expertise.
Entity store, knowledge graph, or flat files (e.g., MEMORY.md, CLAUDE.md)
The memory hierarchy in practice: A coding agent's conversation memory holds the current file edits. Its working memory tracks "which tests are failing." Its episodic memory records "last time I edited this file, the linter failed because of trailing whitespace." Its semantic memory retrieves "the user prefers functional style over classes." Its persistent memory knows "this project uses pytest, not unittest." Each layer reduces wasted work and repeated mistakes.

Context window management is the critical constraint. A 200K-token context window sounds large, but a complex agent session with tool results can fill it in under 50 turns. Strategies for staying under the limit:

Sliding Window
  • Keep the last N messages
  • Simple but loses important early context
  • Works for short, focused tasks
Summarization
  • Periodically summarize old messages
  • Preserves key decisions and findings
  • Lossy — details get compressed out
Delegation
  • Spawn sub-agents for sub-tasks
  • Each gets its own fresh context window
  • Parent receives only the summary result
Guardrails & Safety

An agent with tools is an agent with real-world consequences. It can delete files, send emails, execute queries, and modify infrastructure. Guardrails are not optional — they are the engineering that makes agents safe to deploy. Defense in depth: every layer assumes the layer above it has failed.

1
Input Validation
Prompt injection detection before the input reaches the model. Content filtering for PII, sensitive data, and adversarial payloads. Input sanitization strips control characters and encoding attacks. A separate classifier model can score injection likelihood before the main model processes the prompt.
2
Output Validation
Schema enforcement on every tool call — validate arguments against JSON Schema before execution. Fact-checking assertions against known data. Content moderation on generated text. Output length limits to prevent runaway generation. A second LLM call can review the output before it's returned to the user.
3
Sandboxing & Permissions
Tool execution in isolated containers with minimal permissions. Read-only database connections for query tools. File system access scoped to specific directories. Network egress filtered by allowlist. Each tool declares its permission requirements; the runtime enforces them regardless of what the model requests.
4
Rate Limiting & Cost Control
Per-session token budgets to prevent runaway agents. Tool call rate limits (max N calls per minute). Cost caps per user, per task, and per day. Circuit breakers that kill the agent loop after N consecutive failures. Billing alerts when spend exceeds thresholds.
5
Human-in-the-Loop
Approval gates before destructive actions. The agent pauses and presents its plan: "I'm about to delete 3 files and push to main. Approve?" Configurable per tool — read operations auto-approved, write operations require confirmation. Escalation paths for ambiguous situations where the model is uncertain.
6
Monitoring & Observability
Trace every tool call: input, output, latency, cost. Log every LLM decision with the reasoning that led to it. Structured traces (OpenTelemetry spans) for the full agent loop. Dashboards for token usage, error rates, and tool call patterns. Alerting on anomalies — sudden spike in API calls, unexpected tool invocations, or cost overruns.
The permission model is the guardrail. The single most important design decision is what tools the agent can access and what those tools can do. A query_database tool that accepts arbitrary SQL is fundamentally different from one that only accepts parameterized queries against predefined views. The model will eventually try to do something unexpected — the tool's permission scope determines whether that's harmless or catastrophic. 
// Example: Permission-scoped tool definition
{
  "name": "modify_user",
  "allowed_operations": ["update_email", "reset_password"],
  "blocked_operations": ["delete_account", "change_role"],
  "requires_approval": ["reset_password"],
  "max_calls_per_session": 5,
  "audit_log": true
}
Real-World Agent Patterns

Theory becomes useful when applied. These four patterns appear repeatedly across production agent systems. Each follows the same core loop — observe, reason, act — but adapts it to a specific domain with domain-specific tools, evaluation criteria, and termination conditions.

Code Generation Agent
Write → Test → Fix
The agent receives a feature request or bug report. It reads the relevant code, writes a solution, runs the test suite, reads any failures, and iterates until tests pass. The test suite is the oracle — it provides an objective signal for whether the agent's work is correct, removing the need for human evaluation on each iteration.
Tools: read_file, write_file, run_tests, grep, lint
Data Analysis Agent
Query → Visualize → Interpret
The user asks a question about their data. The agent formulates SQL, runs it, generates a visualization, and interprets the results in natural language. If the first query doesn't answer the question fully, it refines. The key challenge is translating vague questions into precise queries — "how are sales doing?" requires the agent to infer time range, metric, and comparison baseline.
Tools: query_database, create_chart, describe_schema, get_sample_data
Customer Support Agent
Classify → Route → Resolve
Classifies the incoming request (billing, technical, account), retrieves relevant context (order history, account status, past tickets), attempts resolution using approved playbooks, and escalates to a human agent when confidence is low or the action requires authorization. The escalation decision is the hardest part — too aggressive wastes human time, too conservative frustrates users.
Tools: search_tickets, lookup_order, apply_credit, create_ticket, escalate_to_human
Research Agent
Search → Read → Synthesize
Fan-out searches across multiple sources, reads and extracts key findings, cross-references claims between sources, and synthesizes a cited report. The critical design choice is adversarial verification — the agent actively looks for contradicting evidence before accepting a claim. Sources are ranked by authority, and every assertion in the final report links back to its source.
Tools: web_search, fetch_page, search_papers, extract_claims, verify_claim

End-to-End Agent Pipeline

The common thread across all patterns: the agent has a verifiable success criterion. The coding agent has tests. The data agent has the query result. The support agent has resolution confirmation. The research agent has source citations. Without a clear success signal, the agent loop has no termination condition — it either guesses when to stop or runs forever. Design the success criterion before designing the agent.
