Terraform at Scale: IaC Architecture

Module design, state management, multi-environment patterns, CI/CD automation, and GCP-specific patterns for managing 20+ Terraform repos across a large organization.

Anvesh Jarabani · July 2026 · 14 min read
Why Scale Changes Everything

A single Terraform project is straightforward. One main.tf, one state file, one person running terraform apply from their laptop. But at 20+ repositories with multiple teams, multiple environments, and hundreds of GCP resources, everything breaks. The workflow that worked for one project becomes a liability at scale.

At this scale, five problems dominate: configuration sprawl (copy-paste HCL across repos), state conflicts (two engineers running apply simultaneously), environment parity (dev drifts from prod), blast radius (one bad apply takes down networking for every service), and module governance (who owns shared modules, how do upgrades propagate).

The organizing principle: Treat Terraform like application code. Modules get versioned releases. State files get isolated per service and environment. Changes go through PR review with automated plans. Nobody runs terraform apply from a laptop against production.
Module Architecture

The module hierarchy has three layers: shared modules (reusable building blocks), root modules (per-service deployable units), and environment configs (tfvars that parameterize each deployment). Shared modules are versioned via Git tags. Root modules pin to specific versions. Environment configs change values, not structure.

Shared Modules
  • One repo per module (terraform-gcp-*)
  • Semantic versioned via Git tags
  • Input variables with validation blocks
  • Full terraform-docs auto-generated README
  • Tested with terratest or tftest
Root Modules
  • Per-service or per-domain scope
  • Composes 3-8 shared modules
  • Owns its own state file per environment
  • Pinned module versions: ?ref=v2.4.0
  • Backend config in backend.tf
Module Composition
  • Modules calling modules (max 2 levels deep)
  • moved blocks for safe refactoring
  • Version pinning prevents surprise upgrades
  • Upgrade PRs trigger plan diffs for review
  • Breaking changes require major version bump
Version Strategy
  • Major: Breaking changes, removed variables
  • Minor: New features, new optional variables
  • Patch: Bug fixes, doc updates
  • CHANGELOG.md per shared module
  • Dependabot-style automated upgrade PRs
Anti-pattern: Monorepo with all Terraform in one repo. At 20+ services, the blast radius is too large, CI is too slow, and CODEOWNERS becomes unmanageable. Keep one repo per root module and one repo per shared module. 
# Root module sourcing a shared module with version pin
module "vpc" {
  source = "git::https://github.com/org/terraform-gcp-vpc.git?ref=v2.4.0"

  project_id   = var.project_id
  network_name = "${var.env}-shared-vpc"
  subnets      = var.subnets
  secondary_ranges = var.secondary_ranges
}

module "gke" {
  source = "git::https://github.com/org/terraform-gcp-gke.git?ref=v3.1.0"

  project_id     = var.project_id
  network        = module.vpc.network_self_link
  subnetwork     = module.vpc.subnets["us-central1/platform"].self_link
  cluster_name   = "${var.env}-platform"
  node_pools     = var.node_pools
}
State Management

State is the single most fragile piece of Terraform at scale. A corrupted state file or a concurrent modification can destroy infrastructure. The rules: one state file per service per environment, remote backends with locking, encryption at rest, and strict access controls.

Remote Backend (GCS)
  • GCS bucket per GCP project
  • Object versioning enabled (rollback)
  • Uniform bucket-level access (no ACLs)
  • Customer-managed encryption key (CMEK)
  • Lifecycle: 90-day noncurrent version retention
State Locking
  • GCS backend uses atomic object locking
  • Lock file: .tflock in the same bucket
  • Force-unlock only by infra leads
  • CI/CD handles lock acquisition automatically
  • Stale lock detection: 30-minute timeout
State Isolation
  • Prefix: env/service/terraform.tfstate
  • Separate state per root module per env
  • Cross-service refs via terraform_remote_state
  • Or better: data sources instead of state refs
  • Never share state across environments
State Surgery
  • terraform state mv for refactoring
  • terraform import for adopting existing resources
  • terraform state rm to release resources from management
  • terraform state pull/push for bulk operations
  • Always back up state before surgery
# backend.tf — GCS remote state with per-environment prefix
terraform {
  backend "gcs" {
    bucket = "org-terraform-state-prod"
    prefix = "analytics/terraform.tfstate"
  }
}

# Cross-service reference via data source (preferred over remote_state)
data "google_compute_network" "shared_vpc" {
  name    = "shared-vpc"
  project = var.host_project_id
}
Never: Store state locally. Share one state file across multiple services. Use terraform_remote_state across team boundaries (tight coupling). Let developers force-unlock state without understanding why it was locked.

Workspace vs. directory isolation: Workspaces (terraform workspace select dev) share the same backend config and differ only by state key. Directories use separate backend.tf per environment. At scale, directory-based isolation wins because workspaces share a single backend configuration and make it too easy to accidentally apply dev changes to prod.

Multi-Environment Patterns

Four common patterns exist for managing multiple environments. Each trades off simplicity for safety. The right choice depends on team size, compliance requirements, and how much environment parity you need.

PatternIsolationParityComplexityBest For
tfvars-per-env High Exact Low Most teams
Directory-per-env High Manual Medium Divergent envs
Workspaces Medium Exact Low Small projects
Branch-per-env Low Drift High Never
tfvars-per-environment

Same HCL code, different variable values. One dev.tfvars, one staging.tfvars, one prod.tfvars. CI/CD passes -var-file=envs/prod.tfvars. Guarantees structural parity across environments.

Directory-per-environment

Separate environments/dev/, environments/staging/, environments/prod/ directories. Each calls the same shared modules but can diverge. More flexibility, higher risk of drift.

Workspaces

terraform workspace select dev. Simple but limited: same backend config, terraform.workspace in conditionals. Works for small projects. At scale, too easy to apply to the wrong workspace.

Branch-per-environment

dev branch deploys to dev, main deploys to prod. Sounds intuitive but creates permanent drift: cherry-picks diverge, merge conflicts compound, and nobody can prove dev matches prod.

Environment promotion: dev → staging → prod

Automated Terraform Workflows

Nobody runs terraform apply from a laptop. Every change goes through a PR, gets an automated plan, and is reviewed before apply. The CI/CD system owns the credentials, manages the state locks, and enforces policies.

Spacelift
  • Stack per root module, auto-plan on PR
  • Manual approve for prod, auto-apply for dev
  • Drift detection on configurable schedule
  • OPA/Rego policies evaluated before apply
  • Stack dependencies for ordered deployments
  • Worker pools for private network access
Atlantis
  • Self-hosted Go binary, PR-driven workflow
  • atlantis.yaml per repo for project config
  • Comment-driven: atlantis plan, atlantis apply
  • Simpler model but fewer guardrails
  • No built-in drift detection or policy engine
  • Good for teams that want full control
Terraform Cloud
  • HashiCorp's managed platform
  • Run triggers for module dependency chains
  • Sentinel policy-as-code (HashiCorp proprietary)
  • Built-in cost estimation per plan
  • Private module registry
  • Agent-based execution for private networks
GitHub Actions (DIY)
  • Full control, full responsibility
  • terraform plan on pull_request trigger
  • terraform apply on push to main
  • Credentials via OIDC Workload Identity Federation
  • Plan output as PR comment via actions/github-script
  • Build your own drift detection cron
Why Spacelift for GCP at scale: Worker pools run inside your VPC (private network access to GCP APIs). Stack dependencies model the actual deployment order (networking before compute, IAM before services). Drift detection runs scheduled plans and alerts on changes made outside Terraform. OPA policies block non-compliant resources before they reach production.
GCP-Specific Patterns

Google Cloud's resource hierarchy, Shared VPC model, and IAM system create unique patterns for Terraform. These patterns were developed managing infrastructure across a multi-project GCP organization.

Resource Hierarchy

Project Factory
Create GCP projects programmatically with consistent IAM bindings, API enablement, default networking, budget alerts, and labels. A single terraform-gcp-project-factory module produces a fully-configured project from a minimal set of inputs.
Shared VPC
Hub-and-spoke networking. One host project owns the VPC and subnets. Service projects (analytics, platform, data) attach via google_compute_shared_vpc_service_project. Centralized firewall rules, decentralized compute.
Firewall Rules as Code
All firewall rules in a single terraform-gcp-networking repo. Hierarchical firewall policies at the org and folder level. No console-created rules. google_compute_firewall resources tagged by service, managed through PR review.
Workload Identity
No service account keys. GKE pods authenticate via Workload Identity Federation. CI/CD authenticates via OIDC federation with GitHub/Spacelift. google_iam_workload_identity_pool replaces exported JSON keys entirely.
Organization Policies
Enforce constraints across the org hierarchy. constraints/compute.requireShieldedVm, constraints/iam.disableServiceAccountKeyCreation, constraints/compute.restrictLoadBalancerCreationForTypes. Applied at folder level, inherited by all projects.
Service Account Hygiene
Least-privilege IAM. One service account per application role with google_project_iam_member at project scope (never org scope). Custom roles for fine-grained permissions. Regular audits via gcloud asset search-all-iam-policies.

Governance & Drift Management

Infrastructure governance is the gap between "we wrote Terraform" and "our Terraform actually reflects reality." Drift happens. Engineers click things in the console. Scripts modify resources outside Terraform. Without active governance, the state file becomes a lie.

Drift Detection
Scheduled
Spacelift runs terraform plan on a schedule (every 4 hours for prod, daily for dev). Any non-empty plan triggers a Slack alert. Drift is either reconciled (apply the plan) or adopted (import the resource).
Policy as Code
OPA / Rego
Policies evaluate terraform show -json output before apply. Rules: no public IPs on compute, encryption required on storage, no overly permissive IAM, mandatory labels on all resources.
Cost Estimation
Infracost
Every PR gets a cost diff comment: "+$42/month" or "-$200/month." Alerts on cost spikes above threshold. Monthly cost reporting aggregated across all stacks. Budget alerts at 80% and 100%.
Blast Radius Control
Isolation
Small state files (one per service per env). Networking and IAM in separate root modules from compute. -target for surgical changes when needed. Never modify networking and application in the same apply.
Documentation
Auto-generated
terraform-docs generates README from variable descriptions and outputs. ADRs (Architecture Decision Records) for why infrastructure is structured a certain way. Runbooks for common operations.
Access Control
Least Privilege
CI/CD service accounts with minimal IAM roles. No developer has terraform apply access to prod. State bucket access limited to CI/CD and infra leads. Audit logs for all state file access.

Policy Examples (OPA/Rego) 

# deny_public_ip.rego — block public IPs on compute instances
package terraform.policies

deny[msg] {
  resource := input.planned_values.root_module.resources[_]
  resource.type == "google_compute_instance"
  access_config := resource.values.network_interface[_].access_config
  count(access_config) > 0
  msg := sprintf("Public IP not allowed on %s", [resource.address])
}

# require_labels.rego — enforce mandatory labels
deny[msg] {
  resource := input.planned_values.root_module.resources[_]
  required := {"environment", "team", "cost-center"}
  provided := {k | resource.values.labels[k]}
  missing := required - provided
  count(missing) > 0
  msg := sprintf("Missing required labels %v on %s", [missing, resource.address])
}
The feedback loop: Drift detection finds a change → alert fires in Slack → engineer investigates → either writes Terraform to match reality (adopt) or applies Terraform to overwrite the manual change (reconcile). Neither option is always right. The point is that drift is never silent.
