RAG Architecture Patterns

A practical deep dive into Retrieval-Augmented Generation — from chunking strategies to production evaluation pipelines.

Anvesh Jarabani · July 2026 · 14 min read
Overview

The Problem with Parametric Knowledge

Large language models are trained on static snapshots of the internet. The moment training ends, the model's knowledge begins to decay. A model trained through January 2025 knows nothing about events in February. It cannot reference your company's internal documentation, your product's latest changelog, or the contract you signed last week. When pressed on topics beyond its training data, the model doesn't say "I don't know" — it confabulates. It generates plausible-sounding text grounded in nothing. This is the hallucination problem, and it is the single biggest barrier to deploying LLMs in production systems where accuracy matters.

Retrieval-Augmented Generation solves this by decoupling knowledge from the model. Instead of relying on weights frozen at training time, RAG retrieves relevant documents from an external knowledge base and injects them into the prompt at inference time. The model generates its response grounded in actual evidence — cited, verifiable, and up-to-date. RAG turns an LLM from a closed-book exam taker into an open-book researcher.

Why RAG over fine-tuning? Fine-tuning bakes knowledge into model weights, making it expensive to update and impossible to audit. RAG keeps knowledge external — you can update documents without retraining, trace every answer to its source, and enforce access controls on the retrieval layer. For most enterprise use cases, RAG is the right default.

But RAG is not a single technique — it is an architectural pattern with decisions at every layer. How do you split documents? Which embedding model do you use? Where do you store vectors? How do you search, rank, and compose the final prompt? Each choice affects latency, accuracy, and cost. This article walks through the full pipeline, layer by layer, with practical guidance for each decision.

Chunking Strategies

Splitting Documents for Retrieval

Chunking is the first and arguably most underestimated step in a RAG pipeline. Your retrieval quality has a hard ceiling set by chunk quality — if relevant information is split across two chunks, or buried inside an irrelevant one, no amount of embedding sophistication will save you. The goal is to create chunks that are semantically self-contained: each chunk should represent a single coherent idea, with enough context to be useful on its own.

There is no universal "best" chunk size. Smaller chunks (128–256 tokens) give precise retrieval but lose surrounding context. Larger chunks (512–1024 tokens) preserve context but dilute relevance signals and consume more of the context window. The right choice depends on your document type, query patterns, and embedding model.

▦ Fixed-Size

Split by token count with overlapping windows. Simple and predictable — every chunk is exactly N tokens with M tokens of overlap between neighbors.

  • Deterministic, easy to implement
  • Consistent chunk sizes for batching
  • Overlap preserves boundary context
  • Splits mid-sentence and mid-paragraph
  • No awareness of document structure
  • Overlap inflates index size by 20–40%
Best for: unstructured text
◗ Semantic

Split at natural language boundaries — sentences, paragraphs, or topic shifts detected by embedding similarity between adjacent segments.

  • Chunks align with meaning boundaries
  • Better retrieval precision
  • No mid-thought splits
  • Variable chunk sizes complicate batching
  • Sentence-level can be too granular
  • Topic detection adds preprocessing cost
Best for: articles, reports
☰ Recursive

Split hierarchically: first by headers, then by paragraphs, then by sentences, stopping when each chunk is within the target size. Respects document structure at every level.

  • Preserves document hierarchy
  • Adapts to varied content density
  • LangChain's RecursiveCharacterTextSplitter is production-ready
  • Configuration complexity (separator lists)
  • Can produce very small tail chunks
  • Header detection requires clean formatting
Best for: general-purpose
✍ Document-Specific

Custom splitters for structured formats: Markdown by headers, code by functions/classes, HTML by DOM nodes, tables by rows. Uses the document's own structure as the splitting signal.

  • Highest quality for supported formats
  • Natural semantic boundaries
  • Code chunks are self-contained units
  • One splitter per format
  • Requires well-formatted input
  • Doesn't handle mixed-format documents
Best for: code, markdown, HTML
Practical tip: Start with RecursiveCharacterTextSplitter at 512 tokens with 64-token overlap. Measure retrieval recall on a representative query set. Only switch to semantic or document-specific chunking if recall is below your threshold — the added complexity needs to earn its place.

Chunk Enrichment

Raw chunks lose context that existed in the original document. A chunk from page 47 of a PDF doesn't know it came from chapter 3 of the Q2 Financial Report. Chunk enrichment solves this by attaching metadata: document title, section header, page number, creation date, and sometimes a short summary of the parent section. This metadata can be used for filtering at query time (e.g., "only retrieve from documents published after 2025") and helps the LLM ground its response in a broader context.

A more advanced technique is contextual retrieval: before embedding, prepend each chunk with a brief context statement generated by an LLM (e.g., "This chunk is from the Authentication section of the API documentation and discusses OAuth2 token refresh flows"). Anthropic's research showed this can reduce retrieval failures by up to 49% compared to raw chunks.

Embedding Models

Turning Text into Vectors

An embedding model maps text to a dense vector in high-dimensional space. Semantically similar texts end up close together; dissimilar texts end up far apart. The quality of your embeddings directly determines your retrieval ceiling — if the embedding model doesn't place a relevant chunk near the query vector, it will never be retrieved, regardless of how good your reranker is.

The embedding landscape has matured significantly. The key dimensions to evaluate are dimensionality (higher dimensions capture more nuance but cost more to store and search), context window (how much text the model can embed in a single pass), multilingual support, and benchmark performance on retrieval tasks like MTEB.

Matryoshka embeddings: OpenAI's text-embedding-3 models support truncating output dimensions at query time. You can store 3072-dim vectors for maximum precision but search against 256-dim projections for speed, then re-score top candidates with full dimensions. This lets you trade latency for accuracy without re-embedding your corpus.

Embedding Best Practices

Use the same model for indexing and querying. Embedding spaces are not interchangeable — a query embedded with OpenAI will not match documents embedded with Cohere, even if the text is identical. If you switch embedding models, you must re-embed your entire corpus.

Normalize before storing. Most embedding models output unit-normalized vectors, but verify this. If vectors are not normalized, cosine similarity and dot product will give different results, and some vector databases assume normalization.

Benchmark on your domain. MTEB scores are averages across diverse tasks. A model that ranks #1 overall might underperform on legal text, medical records, or code. Run a retrieval evaluation on 100–200 representative queries from your actual use case before committing to a model.

Vector Stores

Where Embeddings Live

The vector store is the persistent layer of your RAG pipeline. It indexes your embedding vectors for fast approximate nearest neighbor (ANN) search and typically supports metadata filtering, namespace isolation, and basic CRUD operations. The choice of vector store depends on your scale, ops model, and whether you need features like hybrid search or multi-tenancy built in.

☁ Pinecone

Fully managed, serverless option available. Strong metadata filtering, namespaces for multi-tenancy, and a generous free tier. The default choice for teams that don't want to manage infrastructure.

  • Serverless — pay per query, no idle cost
  • Metadata filtering on indexed fields
  • Up to 5M vectors on free tier
  • No hybrid search (dense only)
Managed / Serverless
◆ Weaviate

Open-source with hybrid search (dense + BM25) built in. GraphQL API for complex queries, modular vectorization (plug your own embedding model), and strong multi-modal support.

  • Hybrid search out of the box
  • GraphQL query API
  • Generative search (built-in RAG module)
  • Higher operational complexity
Open-source / Hybrid
▦ pgvector

PostgreSQL extension — add vector search to your existing database. Familiar SQL interface, ACID transactions, and no new infrastructure to manage. HNSW and IVFFlat indexes.

  • No new infrastructure (just a PG extension)
  • SQL queries with vector operators
  • Joins with relational data
  • Performance ceiling at ~10M vectors
PostgreSQL extension
◈ ChromaDB

Lightweight, Python-native, designed for rapid prototyping. Runs in-process or as a server. Minimal configuration, built-in document storage, and a clean API.

  • Zero-config local mode
  • Embeds documents automatically
  • Great for notebooks and prototypes
  • Not designed for production scale
Prototyping / Local
★ Qdrant

Rust-based, built for performance. Rich filtering (nested conditions, geo, datetime), payload indexing, and efficient quantization. Open-source with a managed cloud offering.

  • Rich filtering (nested, geo, range)
  • Scalar and product quantization
  • Multi-vector support (ColBERT-style)
  • Smaller ecosystem than Pinecone/Weaviate
Performance / Rust
Decision framework: Starting a prototype? Use ChromaDB. Already on PostgreSQL? Start with pgvector. Need hybrid search? Weaviate or Qdrant. Want zero ops? Pinecone serverless. The vector store is the easiest component to swap later — standardize your embedding pipeline and the store becomes interchangeable.
Retrieval Patterns

Finding the Right Context

Retrieval is where the "R" in RAG does its work. Given a user query, the retrieval layer must find the most relevant chunks from your knowledge base — fast enough for interactive use (under 200ms), precise enough to avoid polluting the context window with noise, and comprehensive enough to not miss critical information. There are several distinct retrieval strategies, and the best production systems combine multiple approaches.

Dense Retrieval

The baseline approach: embed the query, compute cosine similarity against all indexed vectors, return the top-K nearest neighbors. Dense retrieval excels at semantic matching — it understands that "automobile" and "car" are related even though they share no characters. But it struggles with exact keyword matching: a query for error code ERR_SSL_PROTOCOL_ERROR might retrieve chunks about SSL in general rather than the specific error code.

Sparse Retrieval (BM25)

Traditional keyword search using BM25 (Best Matching 25), the algorithm behind Elasticsearch and Solr. Sparse retrieval excels at exact term matching — product names, error codes, acronyms, and domain-specific jargon. It fails at semantic understanding: a query about "how to fix authentication issues" won't match a document about "resolving login failures" unless both use the same words.

Hybrid Search

Combine dense and sparse retrieval to get the best of both worlds. Run both searches in parallel, then merge results using Reciprocal Rank Fusion (RRF). RRF scores each document based on its rank in each result set: score = 1/(k + rank_dense) + 1/(k + rank_sparse), where k is typically 60. Documents that rank highly in both lists score highest. This simple formula consistently outperforms either approach alone across diverse query types.

Retrieval Pipeline

Reranking

Retrieval returns candidates; reranking selects the best ones. A cross-encoder reranker takes each (query, chunk) pair and produces a single relevance score, unlike embedding models which encode query and chunk independently. This joint encoding is more accurate but too slow to run against the entire corpus — so you retrieve a broad set (top 50–100) and rerank to a narrow set (top 5–10).

Cohere Rerank is the most widely deployed API-based reranker. BGE-reranker-v2-m3 is a strong open-source alternative you can self-host. The reranking step typically takes 50–150ms and can improve retrieval precision by 10–25% — a high-ROI addition to any pipeline.

Multi-Query Retrieval

Users rarely write perfect queries. Multi-query retrieval generates 3–5 reformulations of the original query using an LLM, runs retrieval for each, and merges the results. For example, "how does auth work?" might expand to: "authentication flow architecture", "login and session management implementation", "OAuth2 token handling code". This casts a wider net and reduces the chance of missing relevant chunks due to query phrasing.

Watch the latency budget. Multi-query adds an LLM call (300–800ms) before retrieval. Reranking adds 50–150ms after. A pipeline with both can push total retrieval latency past 1 second. In interactive applications, consider running multi-query retrieval in parallel and caching reranker results for repeated queries.
Generation Patterns

Composing the Final Response

Once you have retrieved and reranked your context chunks, you need to compose a prompt that guides the LLM to generate an accurate, grounded response. This is where prompt engineering meets systems design. The generation layer must handle variable amounts of context, maintain source attribution, manage conflicting evidence, and deliver a coherent answer — all within the constraints of the model's context window.

Context Window Strategies

How you arrange retrieved chunks in the prompt depends on how much context you have relative to the model's window:

▮ Stuff

Concatenate all retrieved chunks into a single prompt. Simplest approach. Works when total context fits comfortably within the window (under 60% of max tokens to leave room for the response).

Low context volume
▦ Map-Reduce

Process each chunk independently ("map" step), then combine the individual summaries into a final answer ("reduce" step). Handles arbitrarily large context at the cost of multiple LLM calls.

High context volume
▶ Refine

Process chunks sequentially, refining the answer with each new chunk. The output from chunk N becomes part of the input for chunk N+1. Produces more coherent answers than map-reduce but is inherently sequential.

Sequential coherence

Citation and Attribution

In production RAG systems, every claim in the response should be traceable to a source document. The standard approach is to number your context chunks in the prompt (e.g., [Source 1], [Source 2]) and instruct the model to cite sources inline. The response might read: "The API rate limit is 1000 requests per minute [Source 2], though enterprise plans can request higher limits [Source 4]."

A more robust pattern is structured citations: instruct the model to output a JSON array of claims, each with a text, source_ids, and confidence field. Your frontend can then render citations as clickable links to the original documents, with confidence indicators. This adds parsing overhead but makes attribution machine-verifiable rather than relying on the model's formatting compliance.

Handling Conflicting Evidence

When retrieved chunks contradict each other — and they will, especially in large knowledge bases with versioned documents — the model needs explicit guidance. Without it, the model will silently pick one version, often the one that appears first in the context. A production-grade system prompt should include instructions like: 

If retrieved sources contain conflicting information:
1. Acknowledge the conflict explicitly
2. Prefer the most recent source (check document dates)
3. If dates are unavailable, present both positions
4. Never silently resolve conflicts by ignoring one source

Streaming with Source Attribution

Streaming responses improve perceived latency but complicate citation rendering. Two common patterns: inline citations (the model emits [1] markers as it streams, and your frontend resolves them into links in real-time) or deferred citations (stream the answer text first, then append a "Sources" section at the end). Inline citations feel more authoritative but require the model to interleave generation with attribution, which some models do inconsistently. Deferred citations are more reliable and easier to implement.

The "Lost in the Middle" problem: Research from Stanford (2023) showed that LLMs pay most attention to information at the beginning and end of the context window, often ignoring content in the middle. Mitigate this by placing the most relevant chunks first and last, or by reducing total context volume so there is no "middle" to get lost in. Reranking your chunks by relevance before stuffing is not optional — it is a direct countermeasure to this failure mode.
Evaluation

Measuring RAG Quality

You cannot improve what you cannot measure. RAG evaluation is uniquely challenging because there are two independent systems to evaluate: the retriever (did we find the right documents?) and the generator (did we produce a correct answer from those documents?). A wrong answer might be the retriever's fault (wrong chunks) or the generator's fault (right chunks, wrong interpretation). Your evaluation framework must distinguish between these failure modes.

Evaluation Frameworks

Building evaluation infrastructure from scratch is a common mistake. Established frameworks handle the hard parts — LLM-as-judge prompting, statistical aggregation, and dataset management. Here are the tools worth evaluating:

Framework Metrics Approach Best For
RAGAS Faithfulness, relevance, context recall, precision LLM-as-judge with chain-of-thought decomposition Comprehensive RAG evaluation

Building an Evaluation Dataset

The most impactful investment you can make is a gold-standard evaluation set: 100–300 (query, expected_chunks, expected_answer) triples drawn from real user queries. This dataset serves as your regression suite — every pipeline change gets scored against it before deployment. Build it incrementally: start with 50 examples, expand as you discover failure modes. Include edge cases: ambiguous queries, queries requiring multi-hop reasoning, queries where the answer is "not found in the knowledge base."

Continuous evaluation: Don't treat evaluation as a one-time gate. Log every production query, its retrieved chunks, and the generated response. Sample 1–5% for human review. Track metric trends over time — a drop in faithfulness after a knowledge base update tells you something is wrong with your new chunks, not your model.

Production Considerations

The diagram above shows the happy path. A production deployment adds several cross-cutting concerns:

Caching

Cache embedding computations (same query = same vector), retrieval results (same vector = same chunks within a TTL), and full responses (same query + same chunks = same answer). A three-tier cache can reduce LLM API costs by 30–50% in workloads with repeated queries.

Access Control

Not all users should see all documents. Implement metadata-based filtering at the vector store layer: tag each chunk with its access group, and filter at query time using the user's permissions. This is cheaper and more reliable than post-retrieval filtering, which can return empty results.

Versioning

When documents are updated, their chunks and embeddings must be re-generated. Use a document hash to detect changes, delete stale chunks by document ID, and re-index. Never mix old and new chunks for the same document — stale chunks cause contradictory context.

Observability

Log the full trace for every query: input query, reformulated queries, retrieved chunk IDs with scores, reranker scores, final prompt token count, and generated response. This trace is your debugging lifeline when users report wrong answers.

Advanced Patterns

Beyond the standard pipeline, several advanced patterns are emerging in production RAG systems:

Agentic RAG wraps the retrieval pipeline in an agent loop. Instead of a single retrieve-then-generate pass, the agent decides whether to search, refine its query, request more chunks, or answer based on what it has. This handles complex questions that require multiple retrieval steps — "Compare our Q1 and Q2 revenue numbers" needs two separate searches. The tradeoff is latency: each agent loop iteration adds 1–3 seconds.

Graph RAG augments vector search with knowledge graph traversal. Entities and relationships extracted from documents are stored in a graph database (Neo4j, Amazon Neptune). At query time, the system retrieves not just similar chunks but also structurally connected information — if a user asks about a person, the graph can surface their team, projects, and related policies without those appearing in the same chunk. Microsoft's GraphRAG implementation demonstrated significant improvements on global summarization tasks.

RAPTOR (Recursive Abstractive Processing for Tree-Organized Retrieval) clusters chunks and summarizes each cluster, then clusters and summarizes the summaries, building a tree of abstractions. Queries can match at any level of the tree, enabling both detailed retrieval ("what is the API rate limit?") and high-level retrieval ("summarize our security architecture") from the same corpus.

Start simple. A basic pipeline — recursive chunking, a good embedding model, a managed vector store, hybrid search with reranking, and the stuff strategy — will handle 80% of use cases. Add agent loops, graph retrieval, and tree indexing only when you have evaluation data proving the basic pipeline is insufficient. Complexity is not sophistication.
