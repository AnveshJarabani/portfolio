MCP: The Model Context Protocol

Anthropic's open standard for connecting AI models to tools, data, and the systems they need to reason about. A deep dive into the protocol that replaced a thousand bespoke integrations with one universal interface.

01. Overview

Before the Model Context Protocol, every AI integration was a bespoke wiring job. Want your LLM to query a database? Write a custom tool definition, handle serialization, manage auth, build error handling. Need it to read files? Different tool, different schema, different integration pattern. Connecting to Jira, Slack, GitHub, your internal APIs — each one required its own adapter, its own conventions, its own maintenance burden.

The result was fragmented context. An AI assistant might have access to your codebase through one integration and your documentation through another, but neither integration knew about the other. There was no shared protocol for capability discovery, no standard way for a model to ask "what can I do here?" and get a structured answer.

MCP fixes this. Released by Anthropic as an open specification, the Model Context Protocol defines a universal interface between AI models and the tools and data they need. Think of it as USB for AI — a standardized connector that lets any model talk to any tool without custom glue code.

Key insight: MCP is not another framework or SDK. It is a protocol — a specification for message formats, capability negotiation, and lifecycle management. The SDKs (Python, TypeScript) are reference implementations, but anyone can build an MCP-compliant server or client from the spec alone.

The protocol follows a client-server architecture inspired by the Language Server Protocol (LSP) that powers IDE intelligence. Just as LSP let editors like VS Code support any language without language-specific plugins, MCP lets AI applications support any tool without tool-specific integrations. One protocol, N servers, M models — full interoperability.

02. Architecture

MCP uses a layered architecture with three distinct roles: Hosts, Clients, and Servers. Understanding the boundary between these layers is critical to building well-behaved integrations.

The Host is the AI application the user interacts with — Claude Desktop, an IDE extension like Claude Code, or your own custom application. The host manages the user experience, controls which servers are connected, and mediates between the model and the protocol layer.

Each host creates one or more Clients. A client is a protocol-level connector that maintains a 1:1 relationship with a single server. This isolation is deliberate: servers cannot see each other, cannot interfere with each other, and each connection has its own lifecycle. The host is the only entity with cross-server visibility.

A Server is a lightweight program that exposes capabilities through the three MCP primitives: tools, resources, and prompts. Servers are designed to be small, focused, and composable. A filesystem server does filesystem things. A database server does database things. You combine them at the host level, not by building monoliths.

Transport layer: The connection between client and server uses JSON-RPC 2.0 messages over a configurable transport. MCP supports stdio for local processes, SSE for HTTP-based communication, and the newer Streamable HTTP transport for production deployments. The protocol is transport-agnostic — the same server logic works over any transport.

03. Primitives

MCP defines three core primitives that servers can expose. Each primitive has a different control model — who decides when and how it gets used — and understanding this distinction is essential for designing good MCP integrations.

Tools
Model-controlled

Functions that the AI model can choose to invoke. The model sees the tool's name, description, and input schema, then decides when calling it would help answer the user's question. This is the most common primitive — and the most powerful.

Examples
read_file(path: string) query_database(sql: string) create_issue(title, body, labels) search_codebase(query: string)
Resources
Application-controlled

Structured data exposed via URI schemes that the host application can attach to the model's context. Unlike tools, the model does not decide to "call" a resource — the application or user selects which resources to include. Think of them as contextual documents.

Examples
file:///src/main.py db://prod/users/schema notion://page/design-doc git://repo/diff/main..HEAD
Prompts
User-controlled

Reusable prompt templates with typed parameters that the user explicitly selects. Prompts are discoverable through the protocol and can generate structured message sequences. They let server authors share domain expertise as composable instructions.

Examples
review_code(language, focus_area) explain_error(stack_trace) summarize_pr(repo, pr_number) migrate_schema(from_ver, to_ver)
Control model matters: Tools are the "hands" of the AI — the model autonomously decides to use them. Resources are the "eyes" — the application decides what to show. Prompts are the "playbooks" — the user explicitly activates them. Misclassifying a primitive (e.g., making something a tool when it should be a resource) leads to poor UX: models calling things they should not, or users unable to access data the model could surface.

Each primitive is registered with the server using a name, description, and (for tools and prompts) an input schema defined in JSON Schema. The description is particularly important for tools — it is the primary signal the model uses to decide whether and when to invoke the tool. A vague description produces unreliable tool usage; a precise one produces targeted, appropriate calls.

04. Building Servers

Building an MCP server is intentionally simple. The official SDKs handle protocol negotiation, message framing, and transport management. Your job is to define what your server can do — register tools, expose resources, declare prompts — and the SDK handles the rest.

Python SDK: The Basics

The Python SDK provides a decorator-based API that makes server creation feel like writing a Flask app. Here is a minimal database server that exposes schema introspection and query execution:

from mcp.server.fastmcp import FastMCP
import sqlite3

# Create the server
app = FastMCP("database")

@app.tool()
def query(sql: str) -> str:
    """Execute a read-only SQL query against the database.
    Only SELECT statements are allowed. Returns results as
    formatted text with column headers."""
    if not sql.strip().upper().startswith("SELECT"):
        raise ValueError("Only SELECT queries are allowed")
    conn = sqlite3.connect("app.db")
    cursor = conn.execute(sql)
    cols = [d[0] for d in cursor.description]
    rows = cursor.fetchall()
    return format_table(cols, rows)

@app.tool()
def list_tables() -> list[str]:
    """List all tables in the database."""
    conn = sqlite3.connect("app.db")
    cursor = conn.execute(
        "SELECT name FROM sqlite_master WHERE type='table'"
    )
    return [row[0] for row in cursor.fetchall()]

@app.tool()
def describe_table(table: str) -> str:
    """Get column names, types, and constraints for a table."""
    conn = sqlite3.connect("app.db")
    cursor = conn.execute(f"PRAGMA table_info({table})")
    return format_schema(cursor.fetchall())

TypeScript SDK

The TypeScript SDK follows the same patterns with a class-based API. Tool registration uses method chaining with Zod schemas for input validation:

import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { z } from "zod";

const server = new McpServer({
  name: "github",
  version: "1.0.0"
});

server.tool(
  "create_issue",
  "Create a new GitHub issue in a repository",
  {
    repo:  z.string().describe("owner/repo format"),
    title: z.string().describe("Issue title"),
    body:  z.string().optional().describe("Issue body (markdown)"),
    labels: z.array(z.string()).optional()
  },
  async ({ repo, title, body, labels }) => {
    const result = await octokit.rest.issues.create({
      ...parseRepo(repo), title, body, labels
    });
    return { content: [{ type: "text", text: `Created #${result.data.number}` }] };
  }
);

Error Handling

MCP distinguishes between tool errors (the tool ran but failed — invalid input, resource not found) and protocol errors (the server itself is broken). Tool errors should be returned as content with isError: true so the model can reason about the failure and retry or adjust. Protocol errors propagate as JSON-RPC error responses.

@app.tool()
def read_file(path: str) -> str:
    """Read contents of a file at the given path."""
    try:
        return Path(path).read_text()
    except FileNotFoundError:
        # Tool error: model can see this and adjust
        raise ToolError(f"File not found: {path}")
    except PermissionError:
        raise ToolError(f"Permission denied: {path}")
Design principle: Good tool descriptions are concise but unambiguous. State what the tool does, what inputs it expects, and any constraints. The model reads your description to decide when to call the tool — it has no other signal. Include boundary conditions: "Only SELECT queries", "Paths must be relative to project root", "Returns at most 100 results".

05. Multi-Server Orchestration

The real power of MCP emerges when you connect multiple servers simultaneously. A single AI session might have a filesystem server for code access, a database server for data queries, a GitHub server for issue tracking, and a monitoring server for production metrics — all connected through the same protocol, all discoverable by the model.

How It Works

The host application maintains multiple client instances, each connected to its own server. When the model needs to act, it sees the combined tool list from all connected servers. Tool names are namespaced to prevent collisions: mcp__filesystem__read_file, mcp__database__query, mcp__github__create_issue.

Cross-Server Workflows

Because the model has visibility into all connected servers' tools, it can compose cross-server workflows without any explicit orchestration code. The model simply calls tools from different servers in sequence, threading context through its reasoning.

Example workflow: "Find the failing test, check the related database migration, and open a GitHub issue." The model calls mcp__filesystem__search to find test files, mcp__filesystem__read_file to read the failure, mcp__database__query to check the migration state, then mcp__github__create_issue to file the bug — four tools, three servers, zero custom orchestration.

Capability Negotiation

When a client connects to a server, they exchange initialize messages that declare supported capabilities. The client advertises what it supports (roots, sampling), and the server declares its primitives (tools, resources, prompts). This negotiation happens once per connection and determines what features are available for the session.

// Server capability declaration (during initialize)
{
  "capabilities": {
    "tools":     { "listChanged": true },
    "resources": { "subscribe": true, "listChanged": true },
    "prompts":   { "listChanged": true }
  },
  "serverInfo": { "name": "database", "version": "2.1.0" }
}

The listChanged flag enables dynamic updates: a server can notify the client when its tool list changes (e.g., after a plugin is loaded), and the client re-fetches the catalog. This keeps the model's view of available capabilities current without reconnecting.

06. Transports

MCP is transport-agnostic — the protocol layer defines message semantics, while the transport layer handles how those messages move between client and server. The choice of transport affects deployment topology, latency, and security boundaries.

Transport Communication Use Case Auth Setup
stdio stdin/stdout pipes Local tools, CLI integration Process-level (OS) Simplest
SSE HTTP POST + Server-Sent Events Remote servers, firewalls HTTP headers / OAuth Moderate
Streamable HTTP Bidirectional HTTP streams Production, scalable deployments Full HTTP auth stack Most flexible

stdio: Local Simplicity

The stdio transport is the simplest: the host spawns the server as a child process and communicates through stdin/stdout pipes. No networking, no ports, no certificates. The host writes JSON-RPC messages to the server's stdin, and reads responses from stdout. Stderr is reserved for logging.

This is the default for local development and is what Claude Desktop and Claude Code use for locally configured servers. The server process inherits the host's filesystem access and permissions, which makes it ideal for tools that need to read and write local files.

SSE: HTTP-Based Streaming

The Server-Sent Events transport runs over HTTP. The client sends requests via HTTP POST to the server's endpoint, and the server streams responses back through an SSE connection. This works through firewalls, proxies, and load balancers — anywhere HTTP works, SSE works.

SSE is a good fit for remote servers running on a different machine or in the cloud. The trade-off is that SSE is unidirectional for streaming — the server can push to the client, but the client must initiate a new HTTP request for each message. This is fine for most use cases but limits certain notification patterns.

Streamable HTTP: The Future

The newest transport option, Streamable HTTP, addresses SSE's limitations. It provides bidirectional streaming over standard HTTP, supports session management, and works with modern infrastructure (reverse proxies, CDNs, container orchestrators). This is the recommended transport for production deployments that need to scale.

Security model: MCP inherits the transport's security properties. For stdio, security comes from process isolation and OS-level permissions. For HTTP transports, you get the full HTTP security stack: TLS, OAuth 2.0, API keys, CORS, rate limiting. The protocol specification mandates that servers must not execute destructive operations without explicit user approval, regardless of transport. Hosts are expected to present tool calls for user confirmation before execution.

07. Integration Patterns

MCP servers fall into recognizable patterns based on what they wrap. Here are the most common archetypes, each with distinct design considerations.

● Filesystem Server
Local file system access with safety boundaries
  • read_file, write_file, list_directory
  • search_files with glob/regex patterns
  • Path sandboxing to project roots
  • Git-aware: respects .gitignore
  • Symlink resolution and permission checks
● Database Server
Schema introspection and query execution
  • list_tables, describe_table for discovery
  • query with read-only enforcement
  • Schema exposed as resources (db://schema)
  • Query result size limits and pagination
  • Connection pooling and timeout management
● API Wrapper Server
REST or GraphQL APIs as MCP tools
  • One tool per API endpoint or operation
  • Auth token management (OAuth refresh)
  • Rate limiting and retry with backoff
  • Response transformation (API JSON to model-friendly text)
  • Pagination abstraction for list endpoints
● Monitoring Server
Observability tools: metrics, logs, alerts
  • get_metrics with time range filtering
  • search_logs with structured queries
  • list_alerts, acknowledge_alert
  • Resources for dashboards and runbooks
  • Prompts for incident investigation workflows
● CI/CD Server
Build pipelines, deployments, environments
  • get_build_status, get_build_logs
  • trigger_deploy with environment targeting
  • list_environments, rollback
  • Resources for build configurations
  • Approval gates for production deployments
● Knowledge Server
Documentation, wikis, knowledge bases
  • search_docs with semantic matching
  • get_page, list_spaces
  • Resources for frequently-referenced docs
  • Prompts for contextual Q&A over docs
  • Cache layer for expensive search operations

Design Guidelines

Across all patterns, the same principles apply:

Keep tools small

Each tool should do one thing. A query_and_format_and_email mega-tool is harder for the model to reason about than three separate tools. Let the model compose.

Fail informatively

When a tool fails, return a message the model can act on: "Table 'users' not found. Available tables: accounts, profiles, sessions." Do not return stack traces.

Limit output size

Models have context limits. A tool that returns a 50,000-row query result is not helpful. Paginate, summarize, or truncate with a signal that more data exists.

Document constraints

Put limits in the tool description: "Max 1000 results", "Read-only", "Requires repo:write scope". The model needs this context to use the tool correctly.

IDE Integrations

MCP has become the standard way IDEs and code editors connect AI assistants to development tools:

Claude Code

Anthropic's CLI tool uses MCP natively. Every tool Claude Code exposes — file reading, code search, bash execution — is an MCP server. Users can add custom servers in settings.json and they appear as additional tools immediately.

VS Code

The Claude extension for VS Code supports MCP servers. Configure them in workspace settings and the model gains access to your database, API docs, or any custom tooling alongside code intelligence.

JetBrains & Cursor

JetBrains IDEs and Cursor both support MCP configuration, letting developers extend their AI coding assistants with project-specific tools and data sources without switching contexts.

Production Considerations

Running MCP servers in production requires attention to reliability and operational concerns:

Rate Limiting

Models can be aggressive tool callers. Your server should enforce per-tool and per-session rate limits. Return a clear "rate limited, retry after X" message so the model can back off intelligently.

Caching

Resource-heavy tools (database schema introspection, API calls with large responses) benefit from caching. MCP resources support ETags and subscription-based invalidation for cache management.

Observability

Instrument your MCP servers with structured logging, metrics (tool call count, latency, error rate), and tracing. OpenTelemetry integration helps correlate MCP calls with broader system traces.

Authorization

MCP supports OAuth 2.0 for remote servers. Implement scoped permissions per tool — a model that can query should not necessarily be able to write. The principle of least privilege applies to AI tool access.

Where MCP is headed: The protocol continues to evolve. Key areas of development include agent-to-agent communication (MCP servers that themselves invoke other MCP servers), streaming tool results for long-running operations, and standardized authentication flows that remove the current friction of configuring credentials per-server. The open specification model means the community is actively shaping these directions.
