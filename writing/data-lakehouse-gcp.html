Data Lakehouse on GCP

Implementing the lakehouse paradigm with Delta Lake, Iceberg, BigLake, and BigQuery — warehouse reliability meets data lake flexibility on Google Cloud.

Anvesh Jarabani · July 2026 · 13 min read
Overview

For years, organizations chose between two paradigms. Data warehouses provided ACID transactions, schema enforcement, and fast SQL — but locked data into proprietary formats with rigid schemas and high storage costs. Data lakes offered cheap object storage, open file formats, and schema flexibility — but lacked transactional guarantees, suffered from the "data swamp" problem, and required glue code to handle consistency.

The data lakehouse combines both. It layers warehouse-grade reliability — ACID transactions, schema enforcement, time travel, fine-grained access control — directly on top of open file formats stored in object storage. No data duplication between lake and warehouse. No ETL pipeline copying Parquet files into a proprietary engine. One copy of the data, multiple consumption patterns.

The key enabler is the open table format — a metadata layer that sits between the query engine and the raw files. Delta Lake, Apache Iceberg, and Apache Hudi each implement this differently, but they share the same goal: make a collection of Parquet files in GCS (or S3) behave like a database table with transactions, schema enforcement, and time travel.

Why not just use BigQuery? BigQuery is excellent for SQL analytics, but it uses a proprietary storage format. A lakehouse stores data in open formats on GCS, giving you engine portability — query with BigQuery, Spark, Trino, Flink, or Presto without moving data. BigQuery now supports this model natively via BigQuery managed tables for Iceberg, bridging the gap.
Table Formats

Three open table formats dominate the lakehouse landscape. Each originated at a different company to solve a specific problem, and each takes a different architectural approach to metadata management, partitioning, and transaction isolation.

Databricks
Delta Lake
Uses a JSON-based _delta_log transaction log stored alongside data files. Each commit appends a new JSON file; periodic checkpoints compact the log into Parquet for fast reads.
  • ACID via optimistic concurrency on the transaction log
  • Time travel — query any historical version by log replay
  • MERGE INTO for upserts (insert/update/delete in one statement)
  • Z-ordering to co-locate related data and reduce scan ranges
  • VACUUM to garbage-collect old data files
  • Deep Spark integration; growing Flink/Trino support
Netflix
Apache Iceberg
Three-level metadata hierarchy: metadata files, manifest lists, and manifest files. Tracks individual data files with column-level statistics for surgical pruning.
  • Hidden partitioning — users query by value, Iceberg handles the physical layout
  • Partition evolution — change partitioning without rewriting data
  • Full schema evolution (add, rename, reorder, drop columns)
  • Snapshot isolation with branching and tagging
  • Engine-agnostic: Spark, Trino, Flink, Presto, Dremio, StarRocks
  • Strongest community momentum as of 2026
Uber
Apache Hudi
Designed for streaming upserts. Offers two storage layouts: Copy-on-Write (CoW) for read-heavy workloads and Merge-on-Read (MoR) for write-heavy workloads with incremental processing.
  • Record-level indexing for fast upserts at scale
  • Incremental queries — process only changed records since last read
  • CoW: full file rewrite on update (fast reads, slower writes)
  • MoR: delta log + base file (fast writes, merge on read)
  • Built-in compaction, clustering, and cleaning services
  • Strong for CDC ingestion and near-real-time pipelines

Convergence trend: The table format landscape is converging. Delta Lake adopted Iceberg compatibility (UniForm), Iceberg is gaining Spark-native improvements, and all three now support each other's data files to varying degrees. For new GCP projects in 2026, Iceberg is the default choice due to BigQuery's native managed table support and the broadest engine compatibility.
GCP Implementation

Building a lakehouse on Google Cloud means composing managed services that each handle one layer of the stack. The architecture separates storage (GCS + open formats), metadata (BigLake metastore), compute (BigQuery + Dataproc), and governance (IAM + column/row-level security).

BigLake
Unified storage API that sits between query engines and GCS. Provides a single metastore for Iceberg/Delta/Hudi tables with fine-grained access control, eliminating direct GCS permissions.
BigQuery External Tables
Query Parquet, Delta Lake, and Iceberg data directly in GCS without loading it into BigQuery's managed storage. Pay only for bytes scanned. Ideal for ad-hoc exploration.
BigQuery Managed Tables
Native Iceberg support — BigQuery creates and maintains Iceberg metadata on your GCS data. Write via BigQuery SQL, read from any Iceberg-compatible engine. Best of both worlds.
Dataproc (Managed Spark)
Fully managed Spark clusters for heavy ETL, ML training, and complex transformations. Supports Delta Lake, Iceberg, and Hudi connectors natively. Autoscaling worker pools.
Dataproc Serverless
Pay-per-query Spark with zero cluster management. Submit PySpark or SparkSQL jobs; infrastructure scales automatically. Ideal for scheduled batch jobs and intermittent workloads.
Cloud Storage (GCS)
The foundation layer. All lakehouse data lives as Parquet files in GCS buckets with lifecycle policies, versioning, and cross-region replication. Storage costs start at $0.02/GB/mo.

Reference Architecture

BigQuery managed tables for Iceberg are the recommended path for most GCP lakehouses. You write data with standard BigQuery SQL (INSERT, MERGE, CREATE TABLE), BigQuery automatically generates and maintains Iceberg metadata and Parquet data files in your GCS bucket, and any Iceberg-compatible engine (Spark, Trino, Flink) can read the data directly from GCS. This eliminates the traditional trade-off between BigQuery's ease-of-use and open format portability.
Medallion Architecture

The medallion architecture (also called multi-hop) organizes lakehouse data into progressive layers of quality. Raw data enters as bronze, gets cleaned into silver, and is aggregated into gold for consumption. Each layer has clear ownership, SLAs, and data contracts.

Layer Details

Bronze Layer

The landing zone. Data arrives in its original format — JSON payloads, CDC change events, CSV uploads. The bronze layer preserves full fidelity: no rows are dropped, no fields are filtered. Append-only writes ensure you can always replay from source.

  • Ingestion metadata: source, timestamp, batch ID
  • No transformations — raw bytes preserved
  • Partitioned by ingestion date for time travel
  • Retained for 90+ days (configurable lifecycle)
Silver Layer

The conformance zone. This is where data engineering happens: deduplication, null handling, type casting, join enrichment, and data quality enforcement. Silver tables have enforced schemas and are the source of truth for downstream consumers.

  • MERGE operations for deduplication and SCD
  • Enforced schemas with column-level data types
  • Data quality checks (Great Expectations, Soda)
  • Slowly-changing dimensions (SCD Type 2)
Gold Layer

The business layer. Dimensional models (star/snowflake schemas), pre-computed aggregates, KPI rollups, and ML feature tables. Gold tables are optimized for read performance — denormalized, partitioned by common query patterns, and Z-ordered for scan efficiency.

  • Fact and dimension tables (Kimball-style)
  • Pre-aggregated metrics by time grain
  • ML feature store tables
  • SLA-bound freshness guarantees
GCP implementation: On GCP, bronze tables are typically BigLake external tables over raw GCS data (minimal cost). Silver and gold tables use BigQuery managed Iceberg tables — BigQuery handles the compute for MERGE/INSERT operations, and the resulting Parquet + Iceberg metadata in GCS is readable by Spark or Trino for workloads that need engine flexibility.
Performance Optimization

A lakehouse is only as fast as its physical data layout. Unlike a traditional warehouse where the engine controls storage layout, in a lakehouse you control how data is organized in GCS. These five techniques make the difference between a full table scan and a sub-second query.

Partition Pruning
Skip entire directories of data files
Organize data into partitions by date, region, or tenant. Queries with partition filters skip all non-matching directories — scanning 1 day out of 365 means reading 0.3% of the data. Use date-based for time-series, hash-based for high-cardinality keys.
Z-Ordering / Clustering
Co-locate related data within files
Z-ordering interleaves the sort order of multiple columns using a space-filling curve. Queries filtering on any of the Z-ordered columns benefit from min/max pruning. In BigQuery, this is called clustering — same concept, automatic maintenance.
File Compaction
Solve the small file problem
Streaming and frequent updates produce thousands of small files. Each file requires a separate metadata entry, manifest lookup, and I/O operation. Compaction merges small files into optimal sizes (128MB-1GB), reducing metadata overhead and improving scan throughput.
Predicate Pushdown
Push filters to the storage layer
Column statistics (min, max, null count) stored in Parquet footers and Iceberg manifests let the query engine skip entire row groups and files without reading them. The filter is "pushed down" from the query engine to the storage reader.
Metadata Caching
Cache manifest and statistics in memory
Reading Iceberg manifests from GCS for every query adds latency. Caching manifest files and column statistics in the query engine's memory (Spark driver, BigQuery slots) eliminates repeated GCS reads. BigLake's managed metastore handles this automatically.
Result Caching
Skip computation for repeated queries
BigQuery caches query results for 24 hours (free, no bytes scanned on cache hit). For Spark, use .cache() or persist intermediate DataFrames to avoid recomputation. Semantic layer tools like Cube.js add application-level pre-aggregation caching.
Iceberg advantage: Iceberg's manifest-level column statistics enable file-level pruning before reading any data. A query on WHERE order_date = '2026-07-01' AND region = 'US-West' can skip 99% of data files based on manifest metadata alone — no partition directory listing required. This is why Iceberg typically outperforms Delta Lake and Hudi on scan-heavy analytical queries.
Schema Evolution

Production schemas change constantly — new columns for features, renamed fields for clarity, wider types for growing values. A lakehouse must handle these changes without rewriting existing data files. This is where table format design differences matter most.

Partition Evolution: Iceberg's Killer Feature

In Delta Lake and Hudi, partitioning is baked into the directory structure: year=2026/month=07/day=08/. Changing partitioning (e.g., from daily to hourly, or adding a new partition column) requires rewriting every data file — potentially petabytes of I/O.

Iceberg decouples partitioning from the physical layout. Partition specs are stored in metadata, and each data file records which partition spec it was written under. When you evolve the partition spec, new data files use the new layout while old files remain untouched. The query planner handles the hybrid layout transparently. 

-- Start with monthly partitioning
ALTER TABLE lakehouse.orders
  SET PARTITION SPEC (month(order_date));

-- Traffic grows. Switch to daily — no rewrite needed
ALTER TABLE lakehouse.orders
  SET PARTITION SPEC (day(order_date));

-- Old files: partitioned by month (still readable)
-- New files: partitioned by day (optimized for recent queries)
-- Query planner handles both transparently
Why this matters at scale: A 50TB orders table with monthly partitioning might need to move to daily partitioning as query volume grows. With Delta Lake or Hudi, this means 50TB of rewrite I/O, hours of compute, and a maintenance window. With Iceberg, it is a single metadata-only ALTER TABLE that completes in under a second.
Operations

Running a lakehouse in production requires ongoing maintenance — managing snapshots, controlling storage costs, monitoring query patterns, and handling data recovery. These are the day-to-day operational concerns that determine whether your lakehouse is a managed platform or a "data swamp with ACID."

Time Travel & Rollback
Every write creates a new snapshot. Query any historical version by timestamp or snapshot ID. Roll back corrupted writes without restoring from backup.
  • Iceberg: SELECT * FROM table FOR SYSTEM_TIME AS OF '2026-07-07'
  • Delta: SELECT * FROM table VERSION AS OF 42
  • Rollback: ALTER TABLE t SET SNAPSHOT = snapshot_id
  • Branch/tag snapshots for dev/staging environments
Retention & Cleanup
Old snapshots and orphaned data files accumulate storage costs. Periodic cleanup is essential — but must preserve enough history for time travel and in-flight queries.
  • Iceberg: CALL expire_snapshots('t', older_than)
  • Delta: VACUUM table RETAIN 168 HOURS
  • Remove orphaned files not referenced by any snapshot
  • GCS lifecycle rules for bronze layer TTL
Monitoring
Track table health metrics to catch problems before they impact query performance. Small file accumulation, metadata bloat, and scan sizes are the key signals.
  • File count per partition (alert on > 1000 small files)
  • Bytes scanned per query (detect missing partition pruning)
  • Snapshot count and metadata file sizes
  • BigQuery INFORMATION_SCHEMA for query patterns
Cost Management
Lakehouse costs are dominated by storage volume and compute scans. Controlling both requires lifecycle policies, right-sized compute, and scan-aware query patterns.
  • GCS storage classes: Standard → Nearline → Coldline by age
  • BigQuery: flat-rate slots vs. on-demand by workload predictability
  • Dataproc Serverless: auto-scales to zero between jobs
  • Partition pruning reduces scanned bytes (and cost) by 90%+
