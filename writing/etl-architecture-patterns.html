ETL Architecture: From Raw to Reporting

Modern data pipeline patterns, tool comparison, orchestration, and data quality

Anvesh Jarabani July 2026 14 min read
Overview

The acronym ETL — Extract, Transform, Load — has described data integration for decades. The traditional pattern was straightforward: pull data from source systems, run transformations on a dedicated middle-tier server (often an expensive appliance from Informatica or DataStage), and load the cleaned result into a warehouse. The transformation layer was the bottleneck — compute-constrained, hard to scale, and owned by a small team of ETL developers writing proprietary mappings.

The cloud era flipped this on its head. When BigQuery, Snowflake, and Redshift made warehouse compute essentially elastic, the question became: why transform data before loading it? Storage is cheap. Compute scales on demand. SQL is the lingua franca every analyst already knows. The result: ELT — Extract, Load raw data into the warehouse, Transform in-place using SQL.

ELT won because it removed the most fragile part of the pipeline. No more Informatica server to scale. No more proprietary transformation language. The warehouse is the transformation engine. Tools like dbt and Dataform formalized this — they compile SQL models into dependency graphs, run assertions, manage incremental loads, and produce documentation. The transformation code is version-controlled, testable, and written in the same SQL that analysts use to query the final tables.

This article walks through the architecture that emerges when you adopt ELT at scale: the layer model that organizes transformations from raw to reporting, the tools that orchestrate them, CDC patterns for real-time ingestion, quality gates at every stage, and the observability that keeps it all running.

Note: This article reflects patterns I use daily across BigQuery and SQL Server environments. The principles are warehouse-agnostic, but code examples lean toward BigQuery SQL and Dataform SQLX where specifics matter.
Layer Model

Every serious data platform has layers. You do not transform source data directly into a dashboard view — that creates a brittle, untestable mess. Instead, data flows through progressive stages of refinement, each with clear contracts about what it contains and who owns it. The five-layer model below is the pattern I have seen work across healthcare BI, SaaS analytics, and financial reporting.

Layer 1
Raw / Staging
Exact replica of the source system. No transforms, no renaming, no deduplication. Append-only with ingestion timestamps and source metadata.
Schema mirrors source • Partitioned by ingestion date • Never modified after write • Full audit trail
Layer 2
Preprocessed / Staged
Light cleaning only. Type casting, null standardization, deduplication, column renaming to snake_case. No business logic.
Consistent types • Deduplicated by PK • Standardized nulls • _loaded_at column added
Layer 3
Processed / Conformed
Business logic lives here. Facts and dimensions, surrogate keys, incremental models, cross-source joins, business date calculations.
Star schema • Surrogate keys • Incremental MERGE • Business rules documented • SCD Type 2 for dimensions
Layer 4
Curated
Semantic layer models, pre-aggregated metrics, feature tables for ML, and cross-domain summary tables.
Pre-aggregations • Metric definitions • Feature store tables • Owned by domain teams
Layer 5
Reporting
Final views optimized for consumption. Dashboard-specific views, API export tables, file extracts, and embedded analytics feeds.
Granted to BI tools • Optimized for read • Materialized on schedule • Stable column contracts
-- Example: Dataform SQLX incremental model (Layer 3) config { type: "incremental", schema: "processed", uniqueKey: ["visit_id"], bigquery: { partitionBy: "DATE(visit_date)" } } SELECT v.visit_id, v.patient_id, p.patient_name, v.visit_date, v.clinician_id, COALESCE(v.duration_minutes, 0) AS duration_minutes, CURRENT_TIMESTAMP() AS _processed_at FROM ${ref("preprocessed", "stg_visits")} v LEFT JOIN ${ref("preprocessed", "stg_patients")} p ON v.patient_id = p.patient_id WHERE v._loaded_at > COALESCE( (SELECT MAX(_processed_at) FROM ${self()}), '1900-01-01' )
Key principle: Each layer should be independently testable and re-runnable. If you can drop and rebuild Layer 3 from Layer 2 without data loss, your architecture is sound. If you cannot, you have hidden state that will eventually cause an outage.
Tools

The modern ELT landscape has consolidated around a few categories: transformation frameworks (dbt, Dataform) that compile SQL into dependency graphs, orchestrators (Airflow, Dagster, Argo) that schedule and monitor execution, and ingestion tools (Fivetran, Airbyte, Datastream) that handle the E and L. Here is how the major players compare.

Dataform
Google Cloud native. Uses SQLX — SQL with a thin JavaScript wrapper for ref(), config {}, and assertions. First-class BigQuery integration, dependency graphs, incremental models, and built-in scheduling via BigQuery Studio. No infrastructure to manage.
SQLX BigQuery-native Managed Free tier
dbt
The industry standard. Jinja + SQL templating, database-agnostic (Snowflake, BigQuery, Redshift, Postgres, Databricks). Massive ecosystem of packages, testing framework, documentation generation. Available as dbt Core (open source) or dbt Cloud (managed).
Jinja+SQL Multi-warehouse Huge ecosystem Open source
Apache Airflow
The veteran orchestrator, not a transformer. DAGs defined in Python, complex scheduling, retries, SLA monitoring. Excellent for heterogeneous pipelines (Spark + SQL + Python + API calls). Available managed via Cloud Composer, MWAA, or Astronomer.
Python DAGs Orchestrator Mature Complex
Argo Workflows
Kubernetes-native workflow engine. Each step runs in its own container, so you can mix Spark jobs, Python scripts, and SQL runners in one DAG. Well-suited for ML pipelines and environments already running on K8s.
K8s-native Container-per-step YAML Mixed workloads
Dagster
The newcomer redefining orchestration around software-defined assets. Type checking, built-in data lineage, observability UI, and first-class support for partitioned assets. Better developer experience than Airflow for greenfield projects.

Change Data Capture

Getting data into the warehouse is half the problem. Change Data Capture (CDC) is the set of patterns for detecting and propagating changes from source systems without full table scans on every run. The choice of CDC strategy determines your latency floor, source system impact, and operational complexity.

Log-Based CDC
Reads the database transaction log (binlog, WAL, redo log) to capture every INSERT, UPDATE, and DELETE. Near-zero source impact, sub-minute latency, captures deletes naturally.
Datastream, Debezium, HVR, Fivetran HVA
Query-Based CDC
Polls source tables for rows where updated_at > last_sync. Simple to implement, but misses deletes and adds query load to the source.
Custom SQL, Airbyte incremental, Fivetran standard
Trigger-Based CDC
Database triggers write change records to a shadow table on every DML operation. Captures everything, but adds write overhead and couples CDC to the source schema.
SQL Server CDC, custom triggers, audit tables
Full Load
Dump the entire table on every sync. Simplest to implement, appropriate for small reference tables or when source systems provide no change tracking.
Any connector, pg_dump, BCP, EXPORT DATA

Query-based Minutes-Hours No Moderate Low

Merge Patterns

Once CDC data lands in the raw layer, you need a strategy for applying changes to the processed tables. The three common approaches:

-- BigQuery MERGE for upsert pattern MERGE INTO processed.dim_clinicians AS target USING preprocessed.stg_clinicians AS source ON target.clinician_id = source.clinician_id WHEN MATCHED AND source._loaded_at > target._processed_at THEN UPDATE SET target.clinician_name = source.clinician_name, target.license_type = source.license_type, target.status = source.status, target._processed_at = CURRENT_TIMESTAMP() WHEN NOT MATCHED THEN INSERT (clinician_id, clinician_name, license_type, status, _processed_at) VALUES (source.clinician_id, source.clinician_name, source.license_type, source.status, CURRENT_TIMESTAMP())
Watch out: MERGE in BigQuery has a limitation — the source and target cannot have more than one match per key. If your CDC stream delivers multiple updates for the same row in one batch, you must deduplicate the source CTE first (keep the latest by _cdc_timestamp).
Data Quality

Data quality is not a phase you bolt on at the end. It is infrastructure that runs at every layer, blocking bad data from propagating downstream. A test that catches a duplicate at Layer 2 saves hours of debugging a wrong dashboard number at Layer 5.

Schema Tests
Not null, unique, accepted values, referential integrity. These are table stakes — every column in every model should have at least not_null and unique where appropriate.
Freshness Monitoring
SLA-based alerts when data is stale. "This table should have rows from the last 2 hours." If it does not, block downstream models and alert the on-call.
Volume Anomalies
Row count deviation detection. If today's load is 50% smaller than the 7-day average, something is wrong upstream. Catch it before it becomes a missing-data ticket.
Business Assertions
Custom rules: "revenue should never be negative," "visit duration must be between 1 and 480 minutes," "every patient must have a primary clinician." Domain-specific, high-value.
Distribution Checks
Statistical tests on column distributions. Z-score on averages, cardinality drift, null-rate spikes. Catches subtle upstream schema changes before they break reports.
Cross-Source Reconciliation
Compare totals between source and warehouse. "Billing system says 1,247 claims; warehouse has 1,245. Investigate the 2 missing." Critical for financial reporting.

Data Contracts

Data contracts formalize the agreement between producers and consumers. The source team commits to a schema, SLA, and quality bar. The consuming team builds against that contract. When either side wants to change it, there is a negotiation — not a surprise breakage at 2am.

Producer Commits
  • Schema (columns, types, not-null constraints)
  • Freshness SLA (data available by 06:00 UTC)
  • Volume expectations (10K-50K rows/day)
  • Breaking change notification (7 days minimum)
  • Semantic versioning on schema changes
Consumer Expectations
  • Only reference contracted columns
  • Handle late-arriving data gracefully
  • Validate at ingestion boundary
  • Report contract violations promptly
  • Pin to contract version, upgrade explicitly
-- Dataform assertion: data freshness check config { type: "assertion", schema: "assertions", description: "Visits table should have data from the last 3 hours" } SELECT COUNT(*) AS row_count FROM ${ref("preprocessed", "stg_visits")} WHERE _loaded_at >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 3 HOUR) HAVING row_count = 0 -- Assertion passes when this returns 0 rows (data IS fresh) -- Fails when it returns a row (no recent data found)
Rule of thumb: Every model should have at least one schema test and one business assertion. If you have 200 models and 50 tests, you are under-tested. Aim for a 2:1 ratio of tests to models at minimum.
Orchestration

Orchestration is the glue that turns individual transformation models into a reliable, repeatable pipeline. It answers: what runs when, in what order, and what happens when it fails? The choice between time-based and event-driven scheduling has downstream implications for latency, cost, and operational complexity.

Time-Based Scheduling
Classic cron: run the pipeline every hour, every 15 minutes, or at 04:00 UTC daily. Simple, predictable, but wastes compute when there is no new data. Use Cloud Scheduler, Airflow schedules, or Dataform cron.
Event-Driven Triggers
Pipeline fires when data arrives: a Pub/Sub message, a GCS file upload, a webhook from the source system. Lower latency, no wasted runs, but harder to reason about ordering and requires idempotent transforms.
Dependency Graphs (DAGs)
Directed Acyclic Graphs define execution order: model B depends on A, model C depends on A and B. The orchestrator resolves the graph and runs tasks in the correct order, parallelizing where possible.
Backfill Patterns
Reprocessing historical data safely. Partition-aware backfills overwrite specific date ranges without affecting current data. Critical after schema changes, bug fixes, or new source integration.
Retry & Alerting
Transient failures (network timeouts, slot contention) should retry with exponential backoff. Persistent failures alert to Slack or PagerDuty. Distinguish between "retry" (transient) and "fail-and-alert" (logic error) failures.
Idempotency
Every pipeline step must be safe to re-run without creating duplicates. Use MERGE instead of INSERT, partition-overwrite instead of append, and deterministic surrogate keys.
Scheduling Strategy Decision Tree
# Airflow DAG: orchestrate Dataform workflow run from airflow import DAG from airflow.providers.google.cloud.operators.dataform import ( DataformCreateWorkflowInvocationOperator, ) from datetime import datetime, timedelta with DAG( dag_id="elt_daily_pipeline", schedule_interval="0 4 * * *", # 04:00 UTC daily default_args={ "retries": 2, "retry_delay": timedelta(minutes=5), "on_failure_callback": slack_alert, }, catchup=False, ) as dag: run_dataform = DataformCreateWorkflowInvocationOperator( task_id="run_dataform", project_id="my-project", region="us-central1", repository_id="analytics", )
Idempotency is non-negotiable. If your pipeline creates duplicates when re-run, you will eventually have an incident. Every model should use MERGE, partition-overwrite, or CREATE OR REPLACE. Test this by running the pipeline twice in a row and asserting the output is identical.
Monitoring & Observability

A pipeline that runs without monitoring is a pipeline that fails silently. Data observability covers five areas: lineage (where does this data come from?), freshness (is it current?), volume (is the expected amount arriving?), schema (has the structure changed?), and cost (are we spending what we expect?).

Lineage Tracking
Know the full path from source to report. When a dashboard number looks wrong, lineage lets you trace backward through every transformation to find where the issue was introduced. Tools: dbt docs, Dataform graph, OpenLineage, DataHub.
Cost Monitoring
BigQuery on-demand pricing can surprise you. Track per-query costs, storage growth, and slot utilization. Set budget alerts and use INFORMATION_SCHEMA.JOBS to find expensive queries. Label every scheduled query for attribution.
SLA Dashboards
Visualize data freshness against committed SLAs. "The daily revenue report should be ready by 07:00." If the pipeline finishes at 07:15, the SLA dashboard shows red before anyone files a ticket.
Failure Alerting
Route alerts to the right channel: pipeline failures to the data engineering Slack channel, data quality violations to the domain team, cost anomalies to the platform lead. Use PagerDuty for P1 (revenue-impacting) failures.
Metadata Management
Data catalogs (DataHub, Amundsen, Google Data Catalog) that document what each table contains, who owns it, and when it was last updated. Without this, every new analyst spends their first week asking "what does this column mean?"
Schema Change Detection
Alert when an upstream source adds, removes, or renames columns. Catch breaking changes at the ingestion boundary, not when a downstream model fails. Use ingestion schema comparison and contract validation.
Monitoring Stack Example
-- BigQuery: find your most expensive queries (last 7 days) SELECT user_email, job_id, ROUND(total_bytes_processed / POW(1024, 4), 2) AS tb_processed, ROUND(total_bytes_processed / POW(1024, 4) * 6.25, 2) AS estimated_cost_usd, TIMESTAMP_DIFF(end_time, start_time, SECOND) AS duration_sec, query FROM `region-us`.INFORMATION_SCHEMA.JOBS WHERE creation_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY) AND state = 'DONE' AND total_bytes_processed > 0 ORDER BY total_bytes_processed DESC LIMIT 20
The cost of not monitoring: I have seen a single unoptimized scheduled query cost $400/day because it scanned a 2TB table every 15 minutes without partition pruning. A 5-minute setup of INFORMATION_SCHEMA.JOBS monitoring would have caught it on day one. Label your queries, set budget alerts, and review the top-10 most expensive queries weekly.
